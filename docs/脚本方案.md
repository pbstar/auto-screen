# 脚本能力方案

## 1. 背景

现状是每个任务都走「截图 → 模型决策 → 动作 → 再截图」的闭环，**一步一次模型调用**。实测一次 25 步的任务（`runs/20261028-145735-c356`）花了约 3 分钟、约 300 万 prompt token，其中 24 步是因为一次输入没生效而在原地空转。

已有的技能（`skills/*/SKILL.md`）只提供策略：它让模型知道「按这个流程做」，但每一步仍然要截图、要问模型。同一个流程跑第 10 次，成本和第 1 次完全一样。

目标：让**已经稳定跑通过的可重复流程**以脚本形式在本地确定性执行，不调用模型；一旦现场与预期不符，立刻停下，交回 AI 或用户。

## 2. 必要性判断

### 2.1 成本对比

| | AI 循环 | 脚本 |
|---|---|---|
| 每一步耗时 | 1.5~3 秒（模型往返） | 0.1~0.4 秒（动作 + 校验） |
| 每一步成本 | 5k~15k prompt token | 0 |
| 稳定性 | 受模型随机性影响，实测出现过 24 步空转 | 确定，同样的输入走同样的路径 |
| 适应性 | 强，界面变了也能自己处理 | 弱，界面变了就停 |

一个 20 步的固定流程：AI 循环约 1 分钟、数十万 token；脚本 5 秒、0 token。只要同一流程一周跑三次以上，写脚本就划算。

### 2.2 适用与不适用

值得写成脚本：

- 流程固定、步骤多（≥ 10 步）、界面版本稳定；
- 参数不同但流程相同（收件人、月份、订单号不一样，动作序列一样）；
- 对时间敏感，需要在某个时刻前后完成。

不该用脚本：

- 一次性任务；
- 界面经常改版；
- 需要「读了内容再决定」的环节（看邮件正文写回复、按页面状态选分支）；
- 不可逆操作可以做，但**必须带确认点**。

### 2.3 结论

**有必要，但定位是加速器而不是替代品。** 脚本必须能失败、能停、能交回 AI；否则只是把「模型空转」换成「静默点错」，稳定性反而倒退。这也是本方案里校验点、失败即停、AI 接管三项是硬要求的原由。

## 3. 与技能的关系

- **技能**：给模型看的策略，解决「这类任务该怎么做」。
- **脚本**：给执行器跑的动作序列，解决「这条已知流程不要每步再问模型」。
- 同一个目录可以并存：`scripts/<id>/script.json` 提供可执行序列，可选的 `SKILL.md` 在脚本失败、AI 接管时继续生效。

## 4. 脚本格式

位置：`scripts/<id>/script.json`，一个目录一份，`id` 用英文 slug（与技能目录规则一致）。

```json
{
  "name": "发考勤邮件",
  "description": "给指定收件人发全勤邮件，发送前确认",
  "params": {
    "recipient": { "type": "string", "required": true, "description": "收件人邮箱" },
    "subject": { "type": "string", "required": true, "description": "邮件主题" }
  },
  "steps": [
    { "action": "click", "point": [0.033, 0.221], "expect": "change", "note": "点写信" },
    { "action": "click", "point": [0.343, 0.333], "expect": "same", "note": "聚焦收件人" },
    { "action": "type", "text": "{{recipient}}", "expect": "change" },
    { "action": "key", "combo": "tab", "expect": "any" },
    { "action": "type", "text": "{{subject}}", "expect": "change", "timeoutMs": 2000 },
    { "action": "ask", "question": "确认发送这封邮件？", "options": ["确认发送", "取消"] },
    { "action": "click", "point": [0.153, 0.231], "expect": "change", "note": "点发送" }
  ]
}
```

字段说明：

- `point`：**归一化坐标**（0~1，相对窗口截图），不是像素。窗口大小或分辨率变了照样成立；页面布局变了则靠 `expect` 发现。窗口宽高比与录制时不一致时直接拒绝运行。
- `text`：支持 `{{param}}` 占位，参数由运行前填写。
- `expect`：`change`（这一步之后画面必须变）/ `same`（必须不变）/ `any`（不校验）。
- `timeoutMs`：等待期望变化的上限，默认 3000，内部按 100ms 轮询画面，不只看一次。
- `ask`：复用现有提问流程（`questions.ts`），用在提交、发送、删除这类不可逆动作之前。

动作集合第一版只开放 `click` / `type` / `key` / `wait` / `wait_for_change` / `ask`，与现有工具一一对应，不新增能力面。

## 5. 执行模型

```
runScript → 截一张基线 → 逐步执行（全程不调模型）→ 每步按 expect 校验 → 完成或失败
```

- 校验复用 `agent/watch.ts` 的灰度签名比对（与 `wait_for_change`、`effect.ts` 同源），缩采样会抹平光标闪烁，不会把「光标没拍到」当成没生效。
- 任何一步校验失败、工具抛错、超时，**立即停止**：不再执行后续动作，事件 `script_failed { step, reason }`。
- 失败后界面给两个选择：
  1. **AI 接管继续**：把已完成步骤、失败步骤与原因作为一条 user 消息注入，构造 `RunContext` 走现有 `runAgent`，从当前画面往下做；
  2. **终止**：回到空闲。
- 脚本执行期间保留全部既有保护：暂停闸门、人工接管检测（用户动鼠标即暂停）、`runs/` 运行日志、每步截图（默认只存校验点，避免占满磁盘）。
- 「一步一个动作」约束的是模型；脚本执行器一次跑完整条序列，正是脚本的意义所在，代价是每一步都必须有可判定的期望。

## 6. 安全边界

- 含 `ask` 的步骤由用户确认后才继续；建议每个脚本在提交类动作前都加一条。
- 首次运行建议在界面上打开「每步截图」，方便复盘每一步的坐标是否点对。
- 脚本里不写账号、密钥等敏感值，统一走参数，由用户在运行前填写。
- 脚本只允许操作选定的目标窗口，与现有工具共用 `core/screen.ts` 的坐标换算，不另起一套。

## 7. 事件与界面

- 新事件：`script_started { name, steps }`、`script_step { index, action, ok, note }`、`script_finished { ok, failedStep?, reason? }`。
- 界面：任务卡上方增加「脚本」胶囊（与技能胶囊同排），选中后按 `params` 生成参数输入框，点「运行脚本」；运行中显示「第 3/7 步：聚焦收件人」，可暂停、终止。
- 运行日志复用 `runs/`，脚本步骤的日志格式与 AI 步骤一致，方便对比同一个流程两种执行方式的耗时与成本。

## 8. 分期

**P1（本方案范围，约 600~700 行）**

- `src/shared/script.ts`：脚本类型与格式校验；
- `src/agent/scripts.ts`：扫描 `scripts/*/script.json`，解析参数、校验合法性（坐标范围、动作白名单、占位符是否都有定义）；
- `src/agent/script-runner.ts`：直线执行、逐步校验、失败即停；
- 主进程 IPC、事件、界面入口（选脚本、填参数、运行、失败后的接管/终止）；
- 文档同步与 CLAUDE.md 规则。

**P2（后续）**

- 从一次成功的 AI 运行一键生成脚本草稿：轨迹里已经有每步的工具与参数，把像素坐标归一化、把具体数据抽成参数，再让模型补 `expect` 与 `note`，写进 `scripts/<slug>/`。
- 这是「自动沉淀技能」的姊妹能力：沉淀产出 `SKILL.md`，录制产出 `script.json`。P1 之后手工写脚本会很难受，P2 基本是必做的。

**P3（谨慎）**

- 循环、条件分支、返回值。真要做，应该让脚本在分支处**调用 AI 决策**，而不是在 JSON 里造一门图灵完备的语言。

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 界面改版后脚本静默点错 | 每步 `expect` 校验 + 提交前 `ask` + 失败即停 |
| 页面加载慢导致误判失败 | `timeoutMs` 内轮询画面，而不是只看一次 |
| 坐标随窗口尺寸漂移 | 归一化坐标；宽高比与录制时不一致直接拒绝运行 |
| 脚本成为第二个没人维护的资产 | 失败时提示「脚本可能过期」，P2 提供一键重新录制 |
| 与 AI 循环的状态互相污染 | 运行器只调用 `core/input.ts` 与 `agent/watch.ts`；AI 接管时构造全新的 `RunContext` |

## 10. 备选方案与取舍

- **只靠技能 + 更便宜的模型**：仍然按步计费，且解决不了模型随机性问题（24 步空转不是模型贵，是模型判断错）。
- **让技能直接写坐标**：违反「技能只写策略不写死坐标」，而且技能由模型解读，坐标写了也不保证被执行，还没有失败检测。
- **生成 Python / nut.js 脚本**：等于在仓库里再维护一套鼠标键盘与坐标换算，绕开了现有的工具层、校验与失败收敛，回退到 AI 也更难。

## 11. 验收标准

- 用一个真实流程（发考勤邮件）写一份脚本，连跑 3 次全部通过，token 消耗为 0；
- 故意改错一处坐标，脚本必须在对应步骤失败停下并给出原因，**不得继续执行后面的动作**；
- 脚本失败后点「AI 接管」，能从当前画面继续完成任务；
- 界面上的暂停、终止、人工接管在脚本执行期间同样生效；
- `npm run typecheck` 与 `npm run build` 通过。
