# 脚本能力方案

## 1. 背景

现状是每个任务都走「截图 → 模型决策 → 动作 → 再截图」的闭环，**一步一次模型调用**。实测一次 25 步的任务（`runs/20261028-145735-c356`）花了约 3 分钟、约 300 万 prompt token，其中 24 步是因为一次输入没生效而在原地空转。

已有的技能（`skills/*/SKILL.md`）只提供策略：它让模型知道「按这个流程做」，但每一步仍然要截图、要问模型。同一个流程跑第 10 次，成本和第 1 次完全一样。

目标：让**已经稳定跑通过的可重复流程**以脚本形式执行。脚本内置在技能目录里，由模型判断时机后一次性调用，执行过程中不调用模型；任一步与预期不符就立即停下，把结果交回模型继续。

## 2. 必要性

### 2.1 成本对比

| | AI 循环 | 脚本 |
|---|---|---|
| 每一步耗时 | 1.5~3 秒（模型往返） | 0.1~0.4 秒（动作 + 校验） |
| 每一步成本 | 5k~15k prompt token | ≈0（整条脚本折合在一次工具调用里） |
| 稳定性 | 受模型随机性影响，实测出现过 24 步空转 | 确定，同样的输入走同样的路径 |
| 适应性 | 强，界面变了也能自己处理 | 弱，界面变了就停 |

一个 20 步的固定流程：AI 循环约 1 分钟、数十万 token；脚本 5 秒、约一次工具调用的 token。

### 2.2 适用与不适用

值得写成脚本：

- 流程固定、步骤多（≥ 10 步）、界面版本稳定；
- 参数不同但流程相同（收件人、月份、订单号不一样，动作序列一样）；
- 对时间敏感，需要在某个时刻前后完成。

不该用脚本：

- 一次性任务；
- 界面经常改版；
- 需要「读了内容再决定」的环节（看邮件正文写回复、按页面状态选分支）。

### 2.3 结论

**有必要，定位是加速器而不是替代品。** 脚本执行期间模型不参与，所以脚本必须自带校验、失败即停、结果回传给模型——否则只是把「模型空转」换成「静默点错」，稳定性反而倒退。

## 3. 与技能的关系

- **技能**：给模型看的策略，解决「这类任务该怎么做」。
- **脚本**：同一流程的确定性版本，给运行器跑，解决「不要每步都问模型」。
- 一对多绑定：`skills/<id>/scripts/<脚本 id>.json` 放在 `SKILL.md` 旁边，一个技能可以有零个或多个脚本；文件名就是脚本 id（工具名要用），显示名用 JSON 里的 `name`。单个脚本解析失败只当它不存在，不影响技能本身和其它脚本。
- 脚本只提供动作序列，不写策略；技能手册负责说明「什么时候用它」。

## 4. 脚本格式

位置：`skills/<id>/scripts/<脚本 id>.json`，一个技能可以有多个；可运行的示例见 [skills/calculator/scripts/calc-12x34.json](../skills/calculator/scripts/calc-12x34.json)（在计算器上点出 12×34，坐标按 396×700 的窗口量出）。文件名用小写英文与短横线（全中文会退化成固定词），工具名按「技能 id + 脚本 id」拼。

```json
{
  "name": "发考勤邮件",
  "description": "在写信页给指定收件人发送全勤邮件并提交",
  "when": "当前画面是邮箱写信页：能看到收件人、主题、正文输入框",
  "confirm": true,
  "precheck": { "titleContains": ["邮箱", "写邮件"] },
  "params": {
    "recipient": { "type": "string", "required": true, "description": "收件人邮箱" },
    "subject": { "type": "string", "required": true, "description": "邮件主题" }
  },
  "steps": [
    { "action": "click", "point": [0.343, 0.333], "expect": "same", "note": "聚焦收件人" },
    { "action": "type", "text": "{{recipient}}", "expect": "change" },
    { "action": "key", "combo": "tab", "expect": "any" },
    { "action": "type", "text": "{{subject}}", "expect": "change", "timeoutMs": 2000 },
    { "action": "click", "point": [0.153, 0.231], "expect": "change", "note": "点发送" }
  ]
}
```

字段说明：

- `when`：给模型看的适用条件，会写进工具描述与系统提示。
- `confirm`：为真时，执行前用 `ask_user` 把参数摆给用户确认一次，适合发送、支付、删除这类不可逆流程。
- `precheck`：执行前的低成本前提校验，第一版只支持窗口标题包含（Chrome 的窗口标题就是页面标题），多个关键字需要全部命中。不满足直接返回错误，一个动作都不执行。
- `point`：**归一化坐标**（0~1，相对窗口截图），不是像素。窗口大小或分辨率变了照样成立；窗口宽高比变了或页面布局改版，只能靠 `expect` 发现。
- `text`：支持 `{{param}}` 占位，参数由模型从任务里填，`required` 的参数缺失时直接报错。
- `expect`：`change`（这一步之后画面必须变）/ `same`（必须不变）/ `any`（不校验）。**缺省是 `any`**，不写就不校验；关键步骤建议写明，否则界面改版后脚本会带着错误状态往下跑。
- `timeoutMs`：等待期望变化的上限，默认 3000，内部按 100ms 轮询画面，不只看一次。

动作集合只开放 `click` / `type` / `key` / `wait` / `wait_for_change`，与现有工具一一对应，不新增能力面。

脚本是**线性的**：没有条件分支，也没有循环。需要判断的地方由模型承担——先用 `ask_user` 问用户，或看一眼新截图再决定调哪个脚本、下一步做什么（见第 10 节 P3）。

## 5. 对模型暴露的形态

脚本以**工具**的形式交给模型，一次调用跑完整条序列：

- 勾选的技能如果带脚本，每个脚本注册一个工具 `run_script_<技能 id>_<脚本 id>`，参数 Schema 由 `params` 生成；工具描述里写 `name`、`description`、`when`、步数、是否需要确认。
- 没勾选带脚本的技能时，这些工具都不注册，系统提示里也不出现任何脚本字样——**不改变原有提示词前缀**，缓存不受影响。
- 系统提示在技能正文之后追加一小段：「本技能提供脚本《发考勤邮件》，共 5 步；当前画面符合「写信页」时优先调用它，调用后以返回结果和新截图为准」。
- 模型不需要记住坐标，也不需要逐步决策；它只需要判断「现在是不是该用」。

## 6. 执行模型

```
模型调用 run_script_X(params)
  → 校验参数 → precheck → confirm（可选）
  → 逐步执行（不调模型），每步按 expect 校验
  → 返回一行结果
```

- 成功：返回「脚本《发考勤邮件》执行完成，共 5 步（发送前已确认）」。模型下一步拿到新截图，继续后续判断或宣布完成。
- 失败：立即停止，返回「脚本《发考勤邮件》第 3 步失败：期望画面变化但没有变化，已停止。当前画面见下一步截图，请按技能手册继续」。模型就在循环里，直接接手。
- 进度：每步向界面发一次 `tool_progress`（「第 3/5 步：聚焦收件人」），时间线上是一条带进度的工具条目。
- 暂停与终止：脚本在步边界检查 `signal` 与 `gate`，与现有等待工具的约定一致（规则 10）。
- 完成后：模型宣布完成时，现有的最终核对照常执行（规则 15），脚本不改变这条裁决。
- 一次脚本执行只占**一步**模型调用；「一步一个动作」的规则仍然成立——模型一次只发起一个工具调用，脚本内部的多步由运行器完成，模型拿到的只是整条脚本的结果。
- **重复执行不需要新机制**：模型看到结果和新截图后，可以再调用同一个脚本，每次调用是一步。技能手册负责交代三件事：起始页面（多数脚本要求先回到起点）、每一轮参数的来源、循环的终止条件；脚本的 `precheck` 与首步 `expect` 兜住「页面不对就立刻失败」。N 次重复的成本是 N 步模型调用，而不是 N×L 步。

## 7. 循环层需要配合的几处

1. **`run_script` 不参与画面变化判定**（`effect.ts`）：脚本内部每步已经校验过，外层再比一次只会误报。
2. **失败收敛**：脚本失败按普通工具失败计数（连续两次失败终止运行）；重复检测（`MAX_REPEATS = 3`）只统计**失败**的调用，成功的调用把计数清零。不能照搬 click / move / drag 的「参数相同即计数」规则，否则「同一个脚本连续成功跑三次」会被误杀，而那正是批量重复要支持的场景。
3. **日志**：脚本的每一步都要落 `runs/`，格式与普通步骤一致，否则事后没法复盘脚本到底点在哪里、哪一步开始偏。
4. **接管检测**：脚本执行期间压住人工接管检测（`busy(true)`），与现有输入类工具一致；用户真的动了鼠标则按暂停处理。

## 8. 安全边界

- 模型只能调用**已勾选技能**里的脚本，不能点名任意脚本。
- 不可逆流程在脚本里标 `confirm`，建议所有涉及发送、支付、删除的脚本都标上。确认**按调用次数生效**：每调一次确认一次，确认框带上「第几次调用」与当次参数——批量发送正是最需要逐项核对的场景，不做「本次运行内只确认一遍」。
- 脚本不能调用模型、不能嵌套调用其它脚本，只能做动作。
- 单个脚本最多 80 步、单次执行最长 5 分钟；单步 `timeoutMs` 最多 60 秒。超限按失败处理。

## 9. 界面

- 脚本在界面上跟着技能走：打开「技能」浮层，带脚本的技能在描述下面把每个脚本列一行「脚本《算出 12×34》 · 7 步」；勾选这个技能，脚本才会在运行时逐个注册成工具。页面层级与目录层级一致——技能目录里放什么，这里就显示什么，不另立一个「脚本」分类。
- 「参考」胶囊只放始终生效的两类只读信息：规则、工具，顶部用一排小分段按钮切换，按钮上带数量。
- 技能浮层底部补一句 `scripts/` 目录的用法，否则这个能力在界面上没有入口。
- 运行中不新增按钮：暂停、终止、时间线进度都复用现有机制。

## 10. 分期

**P1（已实现）**

- `src/shared/script.ts`：脚本类型与格式校验（坐标范围、动作白名单、占位符是否都有定义、步数上限）；
- `src/agent/scripts.ts`：读取 `scripts/*.json`（单个文件解析失败只跳过它），把每个脚本注册成 `run_script_<技能 id>_<脚本 id>` 工具，校验参数与 `precheck`，按调用次数确认；
- `src/agent/script-runner.ts`：直线执行、逐步校验、失败即停、进度上报；每步复用现有工具，坐标换算不另写一套；
- `src/agent/frame.ts`：抽出来的单帧采样，`wait_for_change` 与脚本共用；
- `src/agent/run-context.ts` / `loop.ts` / `tools/index.ts`：脚本工具随运行注册与下发；`run_script_` 前缀的调用按输入工具对待（压住接管检测、截图前等重绘），不参与画面变化判定；
- `SkillSummary` 增加可选的脚本摘要数组，`listSkills` 一并返回，界面挂在技能行下面；
- 脚本每步的进度带 `script` 标记落进 `run.log`；`core/pointer.ts` 的 busy 改成按次数计，确认框弹出时不会提前恢复接管检测；
- 文档同步与 CLAUDE.md 规则。

**P2（后续）**

- **录制**：从一次成功的 AI 运行一键生成 `scripts/<脚本 id>.json`——轨迹里已经有每步工具与参数，把像素坐标归一化、把具体数据抽成参数，再让模型补 `when`、`expect` 与 `note`。这是「自动沉淀技能」的姊妹能力：沉淀产出 `SKILL.md`，录制产出脚本文件。
- `precheck` 支持区域指纹：录制时保存页面骨架区域的灰度签名，运行时比对，比只看标题更稳。
- P1 之后手工写脚本会很难受，P2 基本是必做的。

**P3（谨慎）**

- **批量重复**（几十行数据）：逐次调用是 N 步模型调用，脚本内 `forEach` 加参数列表才能压到 1 步，但要先解决列表从任务文本还是文件读。
- **控制流不做**：`if` 与循环一律交给模型——用 `ask_user` 问用户，或看截图后决定调哪个脚本、下一步做什么。真要做条件，做法也是脚本在判断点**停下交还模型**，而不是在 JSON 里造一门图灵完备的语言；脚本保持线性，出错路径才复盘得清。

## 11. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 模型在错误的时机调用脚本 | `when` 描述 + `precheck` 标题校验 + 脚本首步 `expect`；失败只损失一次工具调用 |
| 界面改版后脚本静默点错 | 每步 `expect` 校验 + 不可逆流程 `confirm` + 失败即停 |
| 参数由模型填写出现幻觉 | `required` 强校验；关键流程 `confirm` 时把参数摆给用户核对 |
| 脚本成为第二个没人维护的资产 | 失败时把原因回给模型与用户；P2 提供一键重新录制 |
| `expect` 写得不扎实 | 录制（P2）按真实轨迹自动生成，配合人工评审 |

## 12. 备选方案与取舍

- **用户手动运行脚本（不走模型）**：入口明确、零风险，但脚本只能从头跑、无法用在长任务中间，也不与技能的手册描述联动。改为工具调用后，模型可以在任务的任意一步使用脚本，代价是要靠 `precheck` 与 `expect` 兜安全。
- **把坐标写进技能，或生成 Python / nut.js 脚本**：前者违反「技能只写策略不写坐标」，后者等于在仓库里再维护一套鼠标键盘与坐标换算；两者都绕开了现有的工具层、校验与失败收敛，模型也接不住失败。

## 13. 验收标准

- 一个真实流程（发考勤邮件）写成脚本，模型在正确时机用**一次工具调用**完成原来 15 步以上的操作，token 消耗相比 AI 循环下降 90% 以上；
- 在错误页面强行调用时，`precheck` 或首步 `expect` 拦住，不执行任何动作；
- 脚本中途失败时模型收到「第 N 步失败」并接着完成任务，整体结果仍然经过最终核对；
- 同一个脚本连续调用三次（参数不同）都能跑完，不会被失败收敛误判成原地重试；
- 脚本执行期间暂停、终止、人工接管都在步边界生效；
- 不勾选带脚本的技能时，系统提示与工具列表与现在完全一致；
- `npm run typecheck` 与 `npm run build` 通过。
